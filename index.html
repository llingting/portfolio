CASE 01

招聘全流程管理系统（飞书多维表格 + AI Agent）

已上线运行
技术栈：飞书多维表格 · 飞书开放 API · Python · 飞书自动化（HTTP 节点） · LangChain（重构中）
背 景

企业招聘流程分散在聊天记录和 Excel 里：候选人信息无沉淀、简历靠人工逐份录入、面试过程无结构化数据，无法复盘和沉淀人才库。

方 案
  • 以在线多维表格为人才库载体，设计 4 张业务表（候选人 / 面试 / 分析结果 / 池），通过关联字段打通招聘全流程；
  • 自研 Python 脚本对接飞书开放 API，实现简历附件 → AI 结构化抽取 → 5 个字段自动回填（最高学历 / 工作年限 / 技能 / 当前公司 / 期望薪资），含类型校验与覆盖策略；
  • 规划简历分析助手与招聘分析 Agent，分析结论写入专门表格形成可复盘的人才数据资产。
关键难点与解法
  • 平台能力边界探测：通过搭建测试自动化节点 + 实测回写，验证了飞书自动化 HTTP 节点可将附件 fileToken 推送至外部服务并回写响应——推翻了"附件喂不进 AI"的预设，为外部 AI 处理链路打开通路；
  • AI 输出格式漂移：旧方案用正则解析 AI 回复，格式一漂就错位。改用 Pydantic Schema 约束输出，校验失败变成可捕获、可重试的明确异常；
  • 高频自动化的部署边界：识别出与现有日报节点共用登录态的风险，确立高频任务独立部署、现有机器只跑每日任务的原则。
结 果
4 张 业务表
全流程数据结构上线，候选人信息统一沉淀
5 个字段 自动回填
简历录入从人工逐项 → 附件上传自动完成
全链路 POC 已验证
附件 fileToken → 外部 AI → 结果回表，实测跑通
诚实标注：自动化 HTTP 桥接为 POC 实测（fileToken 逐字符比对一致）；LangChain 重构版已完成教程与旗舰脚本，尚未替换生产脚本。
CASE 02

私域运营日报 Agent（n8n 自动化流水线）

生产运行中
技术栈：n8n · 企业微信 · Chrome 自动化 · 业务口径设计 · 独立部署策略
背 景

客服团队按线（客服一部 / 胸整 / 客服二部 / 皮肤助理）运营私域，入群、加微、成交数据散在企微后台，人工每天逐线拉数、手工算口径，耗时且口径漂移。

方 案
  • 在 n8n 搭建四条日报自动化节点，每日定时抓取企微数据，自动计算指标并推送日报；
  • 业务口径设计（本案例的核心价值，不只是"跑通流程"）：
    • 入群率：分子分母对齐——排除已进群客户再计算，避免重复计数虚高；
    • 加微率：定位为展示字段，不进考核、不触发告警，防止数据被动作化误用；
    • 当月成交：自 2023-11 起逐月归档、追溯不设起始边界，保证历史可比。
关键难点与解法
  • 登录态共用风险：四条节点共用同一企微登录态与 Chrome profile，互相踢线。识别后确立分层策略——高频自动化必须独立机器部署，现有机器只承载每日一次任务；
  • 口径即产品：发现"分母怎么算"直接决定团队是否达标，把口径定义从代码里抽出来做成可讨论、可修改的显式规则，与业务方逐条确认。
结 果
4 条线 全自动日报
每日定时推送，替代人工逐线拉数
3 项口径 显式化
入群率 / 加微率 / 成交追溯规则与业务方对齐
风险前置 识别
登录态共用问题在扩频前被拦截并制定边界
CASE 03

大促直播数据看板（从 0 到 1 复刻）

方案定稿 · 建设中
技术栈：云晰后台数据源 · ETL · 独立服务部署 · SLA 设计
背 景

大促直播期间运营需要准实时的邀约 / 跟单 / 订单数据，现有看板无法复用，需要从 0 到 1 重建数据通路。

方案（已定稿）
  • 数据源为云晰后台三张业务表（邀约 / 跟单 / 订单），经 ETL 清洗汇聚后供看板消费；
  • SLA 明确写进方案：推送频率每 30 分钟覆盖最新数据，单次导出 ≤ 5 分钟；
  • 架构选型完成：独立服务部署（与现有日报机器隔离）+ 数据库 + 看板层，含幂等、鉴权、失败重试与可观测性四项技术设计。
关键难点与解法
  • 部署边界：复用现有日报机器会撞共享登录态风险（CASE 02 的教训直接复用），方案从第一天就按独立机器设计；
  • 先方案后动手：完成完整方案文档 + 批判性自审（主动暴露两处此前误判）后才进入实施，避免边做边返工。

AGENT SHOWCASE

四个 Dify Agent（演示重建版）

基于真实交付经验重构的可运行演示版，跑在个人 Dify 上，测试数据驱动。提示词里的硬约束全部来自真实项目沉淀——面试可逐条展开。

🔍

招聘流程分析 Agent

输入招聘漏斗数据 → 各环节转化率对照基准 → 定位卡点并给可执行动作。数据不足先追问，不拿半截数据硬分析。
硬约束：无数据支撑的结论必须标【推测】，不编造数字
📄

简历分析 Agent

简历 + JD → 匹配度 / 逐条对照 / 亮点 / 风险 / 建议，结构化输出。对应招聘系统的 AI 评估层。
硬约束：没写的一律「未提及」不推测；反歧视条款（合规要求）；不轻易打 90+ 分
🖥️

服务器运维自助 Agent

分诊式排查：网络路径 → 服务进程 → 应用日志 → 配置，逐层隔离不跳步，面向 Docker / systemd 内网环境。
硬约束：只给建议不假装执行；危险命令 ⚠️ 强制人工二次确认
🗓️

面试协调 Agent

候选人时段 + 面试官忙闲 → 候选时段排序（带推荐理由与风险）+ 邀约话术草稿 + 面试官日程备忘。忙闲双路径：日历自动拉取 / 手动粘贴降级。
硬约束：只提议、只出草稿，输出出现"已安排"即为失职；严禁编造忙闲
诚实标注：本区为演示重建版（可运行、可现场演示），非原生产环境部署——生产版本涉及客户数据不可外展；提示词约束与设计思路与真实交付同源。简历分析与面试协调已接入飞书群机器人（长连接模式，免公网 IP）：简历附件 PDF/docx/图片/扫描件全形态自动解析（含 OCR 粘连污染的"二遍局部重识别"分层修复）→ 分析结果自动落库；面试协调只提议不发送。代码完成并实测，部署配置中。
METHODOLOGY

交付方法论

上面三个案例背后是同一套工作方式——它比单个项目更能预测我下一次交付的质量。

STEP 1

先方案后动手

完整方案文档 + 批判性自审，主动暴露方案漏洞后再实施。

STEP 2

边界先实测

平台能力不靠猜：用最小 POC 验证关键假设（如 HTTP 桥接实测），再定架构。

STEP 3

口径即产品

指标分母怎么算直接决定业务成败，口径显式化、与业务方逐条确认。

STEP 4

诚实交付

三态自评（会/写过/精通），没做过的不写；进行中与已交付严格区分。
